# ConvoRAG

A backend-powered conversational RAG system with document ingestion, semantic search, Redis-based chat memory, and LLM-powered interview scheduling.

ConvoRAG exposes two REST APIs built with FastAPI:

1. **Document Ingestion API**: upload a `.pdf` or `.txt` file, extract its text, split it with one of two selectable chunking strategies, embed the chunks, store the vectors in **Qdrant**, and save the document metadata in an **SQL database**.
2. **Conversational RAG API**: ask questions about the ingested documents in a multi-turn chat, or book an interview in natural language. The RAG pipeline is written by hand (no `RetrievalQAChain`, no LangChain), chat memory lives in **Redis**, and bookings are saved to SQL.

Everything runs at no cost: Qdrant Cloud and Redis Cloud free tiers, the free Groq API, and local embeddings.

| Generate embeddings and store in a vector database       | `app/services/embeddings.py`, `app/services/vector_store.py` (Qdrant)           |
| Save metadata in SQL                                     | `documents` table, `app/db/models.py`                                           |
| Custom RAG (no `RetrievalQAChain`)                       | `app/services/conversation.py`                                                  |
| Redis for chat memory                                    | `app/services/memory.py`                                                        |
| Multi-turn queries                                       | Follow-up questions are rewritten into standalone queries using session history |
| Interview booking (name, email, date, time) using an LLM | LLM router plus validation in `app/services/conversation.py` and `booking.py`   |
| Store booking info                                       | `bookings` table, `GET /api/v1/bookings`                                        |
| No FAISS or Chroma, no UI                                | Qdrant is used; Swagger at `/docs` is auto-generated by FastAPI                 |
| Clean, modular, typed code                               | Layered structure, dependency injection, `mypy --strict`                        |

## Quick start

### Prerequisites

- Python 3.11 or newer
- A free [Groq API key](https://console.groq.com)
- A Qdrant instance and a Redis instance (free cloud tiers are described below)

### 1. Clone and install

**Windows (PowerShell)**

```powershell
git clone https://github.com/arsusan/ConvoRAG.git
cd ConvoRAG
python -m venv .venv
.venv\Scripts\activate
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
```

**macOS / Linux**

```bash
git clone https://github.com/arsusan/ConvoRAG.git
cd ConvoRAG
python -m venv .venv
source .venv/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
```

Installing the CPU build of PyTorch first keeps the download small. Skip that line if PyTorch is already installed.

### 2. Get Qdrant and Redis

**Option A: free cloud tiers (recommended)**

1. Create a free cluster at [cloud.qdrant.io](https://cloud.qdrant.io). Copy the cluster URL (it ends with `:6333`) and create an API key.
2. Create a free Redis database at [Upstash](https://upstash.com) or [Redis Cloud](https://redis.io/cloud) and build the connection URL:
   - TLS (Upstash): `rediss://default:<PASSWORD>@<ENDPOINT>:6379`
   - Without TLS: `redis://default:<PASSWORD>@<HOST>:<PORT>`
3. URL-encode special characters in the password (for example `@` becomes `%40`).

**Option B: local Docker containers**

```bash
docker run -d --name qdrant -p 6333:6333 qdrant/qdrant
docker run -d --name redis -p 6379:6379 redis:7-alpine
```

These match the defaults in `.env.example` (`http://localhost:6333` and `redis://localhost:6379/0`), so no URL changes are needed.

### 3. Configure the environment

```bash
cp .env.example .env          # Windows: copy .env.example .env
```

Open `.env` and fill in your values:

```
GROQ_API_KEY=your_groq_key
GROQ_MODEL=llama-3.3-70b-versatile
QDRANT_URL=https://your-cluster.cloud.qdrant.io:6333
QDRANT_API_KEY=your_qdrant_key
REDIS_URL=rediss://default:your_password@your-endpoint:6379
DATABASE_URL=sqlite:///./data/app.db
```

The `.env` file is ignored by git. Never commit real keys.

### 4. Check the connections (optional)

```bash
python -m scripts.check_connections
```

Expected output:

```
Qdrant OK, collections: []
Redis OK: ok
```

### 5. Run the API

```bash
uvicorn app.main:app --reload
```

On startup the app creates the SQL tables and the Qdrant collection if they do not exist. Open **http://localhost:8000/docs** for the interactive Swagger UI. The first upload downloads the embedding model (about 90 MB) once.

### 6. Try it

Using Swagger at `/docs`, or from a terminal (on Windows PowerShell, use `curl.exe` instead of `curl`):

```bash
# Ingest the sample document
curl -F "file=@sample.txt" -F "strategy=sentence" http://localhost:8000/api/v1/documents

# Ask a question, then a follow-up in the same session
curl -X POST http://localhost:8000/api/v1/chat -H "Content-Type: application/json" \
  -d '{"session_id":"demo1","message":"How long is the internship?"}'
curl -X POST http://localhost:8000/api/v1/chat -H "Content-Type: application/json" \
  -d '{"session_id":"demo1","message":"And who mentors the interns?"}'

# Book an interview
curl -X POST http://localhost:8000/api/v1/chat -H "Content-Type: application/json" \
  -d '{"session_id":"demo2","message":"I am Susan Aryal, book an interview on November 18, 2026 at 11 AM. My email is susan@example.com"}'

# List stored bookings
curl http://localhost:8000/api/v1/bookings
```

## API reference

Interactive documentation is available at `/docs` (Swagger) and `/redoc`.

| Method | Path                | Purpose                                   |
| ------ | ------------------- | ----------------------------------------- |
| `POST` | `/api/v1/documents` | Upload and ingest a `.pdf` or `.txt` file |
| `GET`  | `/api/v1/documents` | List ingested documents, newest first     |
| `POST` | `/api/v1/chat`      | Conversational RAG and interview booking  |
| `GET`  | `/api/v1/bookings`  | List stored interview bookings            |
| `GET`  | `/health`           | Liveness check                            |

### `POST /api/v1/documents`

Multipart form fields:

| Field           | Type                  | Default  | Notes                                    |
| --------------- | --------------------- | -------- | ---------------------------------------- |
| `file`          | file                  | required | `.pdf` or `.txt`                         |
| `strategy`      | `fixed` or `sentence` | `fixed`  | Chunking strategy                        |
| `chunk_size`    | integer               | `800`    | 100 to 4000 characters                   |
| `chunk_overlap` | integer               | `100`    | At least 0 and smaller than `chunk_size` |

Response `201`:

```json
{
  "id": "bc6138c6-f43b-458b-bfcc-e6231de343ce",
  "filename": "hr_rag_demo_documents.pdf",
  "content_type": "application/pdf",
  "size_bytes": 36367,
  "chunking_strategy": "fixed",
  "chunk_size": 800,
  "chunk_overlap": 100,
  "num_chunks": 12,
  "created_at": "2026-11-13T17:22:45.311543"
}
```

Errors: `400` (unsupported type, empty or unreadable file, invalid chunk parameters), `413` (file too large), `422` (invalid form values).

### `POST /api/v1/chat`

Request:

```json
{ "session_id": "demo1", "message": "How long is the internship?" }
```

Reuse the same `session_id` to keep multi-turn context.

Response `200` for a question:

```json
{
  "session_id": "demo1",
  "answer": "The internship lasts three months.",
  "intent": "question",
  "sources": [
    {
      "document_id": "bc6138c6-f43b-458b-bfcc-e6231de343ce",
      "filename": "sample.txt",
      "chunk_index": 0,
      "score": 0.8123,
      "text": "..."
    }
  ],
  "booking_id": null
}
```

Response `200` for a completed booking (real output from a test run):

```json
{
  "session_id": "test_user_001",
  "answer": "Your interview is booked, Susan Aryal. Date: 2026-11-18, time: 11:00, email: susan@example.com. Confirmation ID: 1.",
  "intent": "booking",
  "sources": [],
  "booking_id": 1
}
```

`intent` is one of `question`, `booking` or `cancel_booking`. Errors: `422` (invalid body), `502` (LLM provider failure or missing API key).

### `GET /api/v1/bookings`

Returns every stored booking with `id`, `session_id`, `name`, `email`, `interview_date`, `interview_time` and `created_at`.

## How it works

### Document ingestion

1. **Validate** the file extension and size.
2. **Extract text**: UTF-8 decoding for `.txt`, page-by-page extraction with `pypdf` for `.pdf`.
3. **Chunk** using the selected strategy:
   - `fixed`: a sliding character window of `chunk_size` with `chunk_overlap`. Fast and predictable. The final window is skipped when it would only repeat text already covered.
   - `sentence`: splits on sentence and paragraph boundaries, packs whole sentences up to `chunk_size`, and carries trailing sentences (up to `chunk_overlap` characters) into the next chunk. Sentences longer than `chunk_size` fall back to fixed windows. This keeps ideas intact, which usually helps retrieval.
4. **Embed** all chunks in one batch with normalized vectors.
5. **Store** the vectors and payload (`document_id`, `filename`, `chunk_index`, `strategy`, `text`) in Qdrant, in batches of 64.
6. **Save metadata** (filename, content type, size, strategy, chunk parameters, chunk count, timestamp) in SQL.

### Conversational RAG

Each `POST /api/v1/chat` request runs these steps:

1. Load the session's recent history and any in-progress booking state from Redis.
2. **Route**: an LLM call in JSON mode classifies the intent (`question`, `booking`, `cancel_booking`) and extracts booking details. Relative dates such as "next Monday" are resolved against today's date. If the model returns invalid JSON, the request safely falls back to a normal question.
3. For a **question**:
   1. When there is history, rewrite the message as a standalone question.
   2. Embed it and run a cosine similarity search in Qdrant (`TOP_K` chunks).
   3. Build a prompt that tells the model to answer only from the retrieved context, and generate the answer.
   4. Return the answer together with the supporting chunks.
4. Append the user message and the answer to the Redis history, trimmed to the last `CHAT_HISTORY_TURNS` turns and refreshed with a TTL.

### Interview booking

Booking details can arrive in any order across any number of messages.

1. The router extracts whatever the user provided (`name`, `email`, `date`, `time`).
2. New values are merged into the session's saved booking state in Redis.
3. Code validates the merged state: name length, email format, a valid date that is not in the past, and a valid `HH:MM` time. Invalid values are dropped and the user is told why.
4. If anything is missing or invalid, the assistant asks only for what is still needed.
5. When all four values are valid, the booking is saved to SQL, the Redis booking state is cleared, and a confirmation ID is returned.
6. Saying something like "never mind" cancels the booking in progress.

Example:

```
User:      I would like to book an interview
Assistant: To book your interview, I still need your full name, email address, preferred date, preferred time.
User:      Susan Aryal, susan@example.com, next Monday at 2pm
Assistant: Your interview is booked, Susan Aryal. Date: ..., time: 14:00, email: susan@example.com. Confirmation ID: 2.
```

### Where data is stored

| Data                        | Store                                  |
| --------------------------- | -------------------------------------- |
| Chunk text and embeddings   | Qdrant                                 |
| Document metadata           | SQL, `documents` table                 |
| Interview bookings          | SQL, `bookings` table                  |
| Chat history                | Redis list `chat:<session_id>:history` |
| In-progress booking details | Redis key `chat:<session_id>:booking`  |

## Testing and code quality

Run all checks from the project root:

```bash
pytest -v
ruff check .
mypy app
```

The 16 automated tests need no network, API keys, Docker or model downloads. They override the FastAPI dependencies with an in-memory SQLite database, `fakeredis`, a fake embedder, a fake vector store and a scripted fake LLM.

| Test file               | Covers                                                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `test_chunking.py`      | Window size and overlap, sentence carry-over, oversized sentences, invalid parameters                                           |
| `test_ingestion_api.py` | Both strategies, unsupported extension, empty file, invalid overlap                                                             |
| `test_chat_api.py`      | Grounded answers with sources, multi-turn follow-up rewriting, multi-turn booking, invalid email handling, booking cancellation |

Type checking runs `mypy --strict` with the Pydantic plugin, and ruff enforces style.

## Design decisions

- **Layered structure**: routes handle HTTP, services hold the logic, and schemas define the contracts. Services never import FastAPI, so they are easy to test and reuse.
- **Dependency injection**: components are provided through `app/api/deps.py`, which lets the tests swap in fakes without patching.
- **LLM understands, code decides**: the model interprets language (intent, relative dates), but code validates the details and decides when a booking is complete. The model never writes to the database.
- **Redis for short-lived state**: chat history and half-finished bookings expire automatically and are shared across workers.
- **Swappable parts**: the LLM client works with any OpenAI-compatible endpoint (Groq, OpenRouter, local Ollama), and the SQL layer works with any SQLAlchemy URL.
- **Lazy model loading**: the embedding model loads on first use, which keeps startup and tests fast.
- **Blocking work off the event loop**: embedding and vector search run in worker threads inside the async chat handler.

## Known limitations

- Retrieval searches all ingested documents; there is no per-document or per-user filtering.
- There is no authentication or rate limiting.
- Bookings are not checked for double-booked slots or timezones.
- Relative dates are resolved against the server's current date.
- Scanned PDFs without a text layer cannot be read (no OCR).
- There is no endpoint to delete documents or their vectors.
- SQLite is the default; use Postgres for multi-instance deployments.
- Free cloud tiers can suspend idle clusters; resume or recreate the cluster and re-ingest if that happens.

## Troubleshooting

| Problem                                 | Fix                                                                                      |
| --------------------------------------- | ---------------------------------------------------------------------------------------- |
| `502 GROQ_API_KEY is not configured`    | Set `GROQ_API_KEY` in `.env` and restart the server                                      |
| Qdrant `403` or `Unauthorized`          | Check `QDRANT_API_KEY`                                                                   |
| Qdrant timeout or connection error      | Use `https://` and include `:6333` in `QDRANT_URL`                                       |
| Redis SSL or connection reset error     | The database needs TLS; use `rediss://`                                                  |
| Redis connection refused on `rediss://` | The database does not use TLS; use `redis://`                                            |
| Redis authentication error              | Re-check the password and URL-encode special characters                                  |
| Vector size mismatch                    | After changing the embedding model, update `EMBEDDING_DIM` and delete the old collection |
| Groq `429` rate limit                   | Wait a minute, or set `GROQ_MODEL=llama-3.1-8b-instant`                                  |
| Slow first request                      | The embedding model is downloading; this happens once                                    |
| `ModuleNotFoundError: app`              | Run commands from the project root, not from inside `app/`                               |
